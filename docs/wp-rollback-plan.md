# План за връщане — WooCommerce качване

Написан преди пускането, не след като нещо се счупи.

**Точката за връщане:** `main` е на `2114207` преди сливането. Запиши този номер.
Клонът е на `84dd8c0`, 12 комита напред, `main` не е мърдал — сливането е чисто
пренавиване.

---

## Какво може да се обърка и какво се прави

### 1. Каталогът не се отваря или продукт не се запазва

Най-опасното, защото засяга **всичките 725 продукта**, не само магазина.

Причина: колона липсва в базата. Но това вече е предотвратено — миграциите
влязоха в production преди кода и провериха 10 колони, индекс, 725 продукта.

**Проверка (Supabase SQL editor, production):**

```sql
select count(*) from information_schema.columns
where table_schema='public' and table_name='products' and column_name like 'wp\_%';
```

Очаквано: `10`. Ако е по-малко, пусни отново `docs/production-wp-migration.sql`.

**Ако е 10, а пак не се запазва** — не е от колоните. Върни кода:

```bash
git checkout main && git reset --hard 2114207 && git push --force-with-lease github main
```

Vercel ще пусне нов деплой от предишния код. Около 2 минути.

### 2. Бутонът за качване дава грешка

Засяга само магазина. Каталогът работи. **Не бързай да връщаш.**

Съобщението казва причината:

| Съобщение | Значение | Действие |
|---|---|---|
| „WooCommerce не е настроен" | променливите не са стигнали | нов деплой във Vercel |
| „WooCommerce отказа (401)" | ключът е грешен или само за четене | нов ключ с Read/Write |
| „WooCommerce отказа (400)" | магазинът отхвърля данните | прочети текста, той е от магазина |
| „Продуктът вече не съществува" | записът е изтрит в WordPress | натисни пак, ще се създаде нов |
| „Сайтът е недостъпен" | магазинът не отговаря | изчакай, пробвай пак |

### 3. Качен е грешен продукт в магазина

Изтрий го от WordPress, после изчисти връзката в Prody:

```sql
update products set wp_product_id = null, wp_synced_at = null
where id = '<id на продукта>';
```

Без второто продуктът засяда — макар кодът вече да се самоизлекува при
следващото качване.

### 4. Искаш само да изключиш качването, без да връщаш код

Най-бързото и най-безобидното. Изтрий трите променливи във Vercel:

```
WOOCOMMERCE_URL
WOOCOMMERCE_CONSUMER_KEY
WOOCOMMERCE_CONSUMER_SECRET
```

Следващият деплой изключва бутона — казва „не е настроен". Всичко останало
работи. Нищо в базата не се пипа.

**Това е предпочитаният ход при съмнение.** Спира писането в магазина за
секунди, без да пипаш кода.

---

## Какво НЕ се връща

**Колоните в базата остават.** Не ги трий при връщане:

- Празни са и нищо не ги чете, когато кодът е стар — безобидни са.
- Триенето им е необратимо и губи въведените текстове.
- Ако върнеш кода и после пак го пуснеш, колоните трябва пак да са там.

**Продуктите, вече качени в магазина, остават.** Връщането на Prody не ги
трие — те са отделни записи в WordPress. Трият се на ръка.

---

## Ред при пускане

1. ✅ Миграциите в production — направено, потвърдено (10 колони, 725 продукта)
2. ✅ Ключовете във Vercel — направено, само Production, без `NEXT_PUBLIC_`
3. ⬜ Сливане в `main` → Vercel деплойва сам
4. ⬜ Отвори каталога, отвори продукт, запази без промяна — **това е важната проверка**
5. ⬜ Чак тогава пробвай качване, с един продукт

Стъпка 4 е същинската. Ако запазването работи, най-лошото е избегнато.

---

## Какво е проверено преди пускането

- 622 от 624 продукта имат снимка — снимките **не** се качват в тази версия
- Само натиснат бутон пише в магазина; нищо автоматично
- Ключовете не стигат до браузъра — четат се само на сървъра
- Никой отговор не носи ключ или адрес
- Миграциите само добавят nullable колони, нищо не трият
- Самолечението при изтрит запис е проверено срещу истинския магазин

**Непроверено:** спирането при празно заглавие. Ако не сработи, ще се създаде
продукт без име в магазина — вижда се веднага и се трие лесно.
